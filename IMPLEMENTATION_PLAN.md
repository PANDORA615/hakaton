## 1. Что создаём

Веб-приложение для маркетолога, отвечающее на три вопроса:

1. Каким клиентам требуется внимание?
2. Какие факторы повышают риск непродления?
3. Какой объём платежей может оказаться под риском?

Основной сценарий: открыть рейтинг → выбрать клиента → увидеть услуги, риск, причины и денежную оценку → изменить коэффициент или исходные данные → увидеть пересчитанные результаты без перезагрузки страницы.

Приоритет первого релиза — все обязательные условия приёмки. OIDC, расширенная аналитика и дополнительные графики идут после них.

## 4. Шаг 1 — использовать изученный набор и реализовать импорт

### 4.1. Что подтверждено проверкой файлов

Пользователь предоставил семь файлов с диска организаторов. Прочитаны схема, откат, seed, JSON, README, генератор и тесты. Суффикс `(1)` у имён прикреплённых Python-файлов и README — отличие имён загрузки; тест ожидает соседний `generate.py`.

| Файл | Содержимое и результат проверки | Как используем |
| --- | --- | --- |
| `001_schema.up.sql` | PostgreSQL: accounts, services, transactions, CHECK/FK/индексы, identity | Основа миграции исходного слоя, не готовая схема всего приложения |
| `001_schema.down.sql` | DROP трёх таблиц вместе с данными | Только явно выбранный откат; не часть запуска/остановки |
| `002_seed.sql` | Транзакционная загрузка только в пустые таблицы, блокировка, setval | Проверка совместимости; не механизм PUT snapshot |
| `data.json` | 10 accounts, 30 services, 100 transactions | Основной вход для адаптера и первого запуска |
| `generate(1).py` | Детерминированный генератор без внешних библиотек | Копия под именем generate.py для воспроизводимых и нагрузочных наборов |
| `README(1).md` | Описание формата, ограничений и опорной даты | Документ происхождения; сохраняем рядом с оригиналом |
| `test_generate(1).py` | Три unittest-проверки | Переносим в отдельный каталог fixtures с ожидаемыми именами |

Фактические результаты проверки:

- Для каждой из трёх сущностей JSON внутри SQL совпадает с массивом из data.json.
- Генератор с seed=42 и reference=`2026-10-19T15:00:00.000Z` воспроизводит предоставленный JSON и SQL без различий.
- Три теста прошли: связи/диапазоны/даты, воспроизводимость/другие размеры, некорректные количества. Для запуска использованы временные копии с именами generate.py и test_generate.py; оригиналы не изменены.
- Услуги: по шесть каждого статуса; по пять каждого периода оплаты.
- Транзакции: 67 performed и 33 not_performed. Аккаунты: пять locked и пять unlocked.
- SQL на сервере PostgreSQL в этой проверке не выполнялся. Совпадение JSON/SQL не заменяет интеграционный тест миграции и seed.

### 4.2. Фактический DTO

Корень data.json — объект с тремя массивами `accounts`, `services`, `transactions`. Поля `schema_version` в исходнике нет. `PUT /api/v1/source/snapshot` обязан принимать исходный объект напрямую. Версию адаптера и метаданные времени храним отдельно; расширенный envelope может быть дополнительным форматом.

| Сущность | Поля | Ограничения исходной SQL-схемы |
| --- | --- | --- |
| accounts | id, email, balance, withdrawBalance, totalReplenished, bonusBalance, bonusState | id bigint PK; email NOT NULL UNIQUE с учётом регистра; суммы bigint >= 0; bonusState locked/unlocked |
| services | id, name, ownerId, paymentTerm, autoProlong, createdAt, expiresAt, status, price | ownerId → accounts.id; price bigint >= 0; autoProlong boolean; даты timestamptz(3), expiresAt >= createdAt; имя по шаблону ^[A-Za-z0-9-]+$ |
| transactions | id, amount, status, performedAt, createdAt, type, serviceId | serviceId → services.id; amount integer 0–1000; type order/prolong; performed требует performedAt >= createdAt; not_performed требует performedAt=null |

Критически важно: поле называется **autoProlong**, с заглавной P. Внешний JSON сохраняет это имя; внутри Python допускается auto_prolong с Pydantic alias. Аналогично маппим ownerId, serviceId, paymentTerm и даты. В SQL camelCase заключаем в двойные кавычки.

Не добавляем несуществующую связь transactions.ownerId: владелец определяется через serviceId → services.ownerId. Не расширяем allowlist статусов и периодов без версии адаптера. Для целых полей используем строгую валидацию: boolean не является допустимым денежным значением или ID.

Уникальность email в исходной схеме чувствительна к регистру; адаптер не приводит email к нижнему регистру молча. Не навязываем `withdrawBalance <= balance` и `totalReplenished >= balance`: генератор соблюдает их, но схема не объявляет бизнес-правилом.

Предел amount <= 1000 относится к контракту этого комплекта. Сохраняем для исходного адаптера и документируем; перед интеграцией с другим источником потребуется отдельное согласование диапазона, а не незаметное ослабление CHECK.

### 4.3. Особенности, влияющие на модель

Опорная дата генератора — `2026-10-19T15:00:00.000Z`, то есть 19 октября 2026 года, 18:00 по Москве. В JSON сама опорная дата не записана: сохраняем её в манифесте комплекта на основании генератора/README.

- Все шесть prolong_wait имеют expiresAt раньше опорной даты на 35–400 дней (максимум около 399.958 дня). Это не согласуется с пятидневным ожиданием оплаты из кейса.
- Из шести suspended две услуги просрочены на 40 и примерно 58.958 дня уже на опорную дату. У всех шести active на опорную дату сроки ещё не истекли.
- Сдвиг as_of на опорную дату не исправляет перечисленные несогласованности. При использовании текущего времени часть других услуг также окажется просроченной.
- В этом наборе у каждого клиента три услуги одинакового статуса: клиенты 2/7 имеют только blocked, 3/8 — только deleted. Это ограничение разнообразия примера, не бизнес-правило. Клиентов с разными статусами добавляем отдельными сценариями.
- Транзакции имеют createdAt и performedAt: доступен факт выполнения конкретной операции. Но это синтетический набор, суммы генерируются независимо от price; ни одна из 100 сумм не равна цене связанной услуги. Поэтому баланс, доход и дату последнего фактического продления нельзя восстанавливать из этих операций без дополнительного контракта.
- Истории смены статусов услуг, времени удаления и признака фактического оттока по-прежнему нет. Даты операций не заменяют эту историю.
- По README даты услуг задают один оплаченный период. Принимаем price за цену одного paymentTerm как явное допущение для модели; будущую интеграцию с источником проверяем отдельно.

**Политика качества:** нарушения типов, CHECK, уникальности и FK отклоняют snapshot целиком. Семантические противоречия жизненного цикла сохраняются с предупреждениями: `payment_wait_beyond_grace`, `renewable_status_with_past_expiry`. Их не исправляем и не переводим в deleted автоматически. Для таких услуг базовый прогноз и денежная оценка — unknown до получения согласованного состояния. На карточке сохраняем наблюдаемый статус и показываем конкретное противоречие.

### 4.4. Практическая последовательность

1. Сохранить семь оригиналов в `data/original/` без редактирования, записать SHA-256 и происхождение. Примеры email имеют домен example.test; возможность публикации полного набора проверяем по условиям организаторов.
2. Создать `SourceSnapshotDTO` с точными именами/alias и отдельный отчёт структурной валидации и семантического качества.
3. Перенести исходную схему в Alembic с сохранением ограничений и FK. Добавить отдельные миграции таблиц приложения, сессий, настроек, расчётов и метаданных snapshot.
4. Реализовать импорт из JSON в пустую БД. Для первого запуска выбрать этот путь как единственный автоматический seed; не выполнять параллельно 002_seed.sql, иначе будут дубли/конфликты.
5. Реализовать PUT как замену данных через staging и транзакцию. Проверять всё до публикации. Исходный SQL seed не подходит для повторной загрузки и требует пустых таблиц.
6. При физической замене удалять источник в порядке transactions → services → accounts и вставлять в обратном порядке. Производные результаты связывать с версией/снимком, чтобы их FK не мешали замене и старая опубликованная версия оставалась читаемой до готовности новой. Не отключать FK ради импорта.
7. Учесть identity-последовательности при явных ID. Повторный идентичный PUT не создаёт дубли; допускается новая версия snapshot, но состав сущностей тот же.
8. Создать отдельные детерминированные сценарии: low/medium/high, locked/unlocked, общий дефицит нескольких услуг, prolong_wait внутри пяти дней, unknown, смешанные статусы и границы календаря. Не редактировать для этого оригиналы.
9. Реализовать явный режим времени: фиксированный as_of для оригинального примера и live UTC для согласованных событий. В панели отображать режим и предупреждения. В live-демо генератор базового набора сам по себе недостаточен: нужен сценарный набор со согласованными статусами и датами.

Готовность: комплект прочитан и проверен; далее требуется работающий DTO/импорт, отчёт качества, интеграционный тест PostgreSQL и сценарные данные для приёмки. Исследование файлов завершено, реализация импорта ещё не выполнена.

## 5. Шаг 2 — определить предметную модель

### Деньги

- Все входные суммы — еврокопейки: 100 единиц = 1 EUR.
- Деньги храним целыми числами; коэффициенты и промежуточные вычисления выполняем через Decimal.
- Перевод в EUR и округление отображения выполняем на границе API/UI по единому правилу.
- Доступные средства: `max(balance, 0) + max(bonusBalance, 0)`, если bonusState = unlocked; иначе (locked) только `max(balance, 0)`. Отрицательные входные суммы отклоняем при импорте, а не исправляем через max; защитное ограничение в формуле не скрывает ошибку источника.
- `withdrawBalance` не включаем автоматически: его доступность для вывода или ручного перевода не означает доступность для автосписания.
- `totalReplenished` — исторические пополнения, а не текущий доход, баланс или величина будущих потерь.
- Доступные бонусы показываем отдельно: покрытие бонусами не равно будущему поступлению реальных денег.

### Статусы услуг

| Статус | Интерпретация в системе |
| --- | --- |
| active | Действующая услуга, оцениваем ближайшие продления |
| suspended | Выключена пользователем, но оплата продолжается; сам статус не доказывает отток |
| prolong_wait | Ожидание оплаты; по кейсу после expiresAt есть пять дней до удаления |
| deleted | Уже удалена; не включаем в будущий риск продления |
| blocked | Продление невозможно; исключаем из прогноза продлений, показываем отдельно |

Не создаём даты прошлых удалений из текущего статуса. `expiresAt + 5 дней` — расчётный срок по правилам кейса для ожидания оплаты, а не наблюдавшаяся дата удаления. Несогласованные состояния, например prolong_wait значительно дольше пяти дней, помечаем как проблему качества данных.

Транзакция `not_performed` может означать неоплаченный заказ, а не подтверждённую ошибку платежа. В фактическом DTO есть createdAt и serviceId, но нет даты отмены или причины неоплаты. Долю неоплаченных операций можно показывать справочно, однако в начальный score не включаем: генератор задаёт статусы и суммы синтетически. Не вычисляем баланс и totalReplenished из этих транзакций.

Готовность: эти правила документированы и покрыты граничными примерами до разработки формул.

## 6. Шаг 3 — реализовать объяснимый risk-score

### Почему начинаем с правил

В примере нет истории изменения статусов и дат удаления; на такой основе нельзя честно заявить обучение и проверку вероятностной модели оттока. Первый вариант — настраиваемый индекс риска, а не доказанная вероятность ухода. После накопления наблюдений можно проверить калибровку и обучить модель.

Базовый горизонт `H = 7 дней`, окно близкого окончания `T = 3 дня`, пересчёт по событиям и минимум раз в минуту из-за течения времени. Это выбранные параметры, а не требования организаторов. Значения изменяются через настройки.

### Начальные признаки для услуги

Для каждой услуги, которую возможно продлить и чьё состояние прошло семантическую проверку раздела 4.3, получаем признаки в диапазоне `[0; 1]`. Не включаем заведомо противоречивую просрочку в score как нормальный prolong_wait.

| Код | Расчёт | Начальный вес | Причина для пользователя |
| --- | --- | ---: | --- |
| no_autoprolong | 1, если autoProlong=false и есть платёж в H; иначе 0 | 25 | «До оплаты N дней, автопродление отключено» |
| funding_gap | Непокрытая часть платежей услуги в H / сумма её платежей; 0 при отсутствии платежей | 30 | «На ближайшие продления не хватает X EUR» |
| payment_wait | 1 для prolong_wait, иначе 0 | 30 | «Услуга ожидает оплаты» |
| expiry_urgency | max(0, 1 − max(days_to_expiry, 0) / T), при корректной дате и согласованном статусе | 15 | «Срок оплаты наступил или близок» |

Отсутствующий признак хранится как `null`, а не как 0. При нулевой сумме платежей funding_gap = 0 допустим только когда расписание известно; отсутствие цены или даты не означает отсутствие обязательств.

Предлагаемая формула:

```text
coverage = сумма весов доступных признаков / сумма всех включённых весов
service_score = 100 × сумма(weight × feature) / сумма весов доступных признаков
```

Оценку не публикуем, если coverage < 0.75, нет корректной даты/статуса для определения жизненного цикла или сумма доступных весов равна нулю. Порог покрытия редактируется. Возвращаем `score=null`, `risk_level=unknown`, `missing_fields`, `coverage` и понятную причину.

Начальные уровни: low при `0 ≤ score < 30`, medium при `30 ≤ score < 60`, high при `60 ≤ score ≤ 100`. Классифицируем по неокруглённому score, отображение округляем отдельно.

Индекс клиента — максимальный индекс его продлеваемых услуг: так риск одной услуги не теряется среди нескольких благополучных. Это сигнал для контакта с клиентом, а не вероятность ухода всего аккаунта. Если хотя бы одна учитываемая услуга не оценена, общий уровень клиента — unknown; отдельно показываем максимум известных услуг как частичный результат. При отсутствии продлеваемых услуг — unknown с причиной «нет услуг для оценки будущего продления».

Вес 0 отключает признак. Все веса неотрицательны, хотя бы один положителен; `0 < T ≤ H`, пороги строго упорядочены, параметры конечны. Некорректный PATCH отклоняется целиком. Причины показывают фактическое значение, вес и вклад; для низкого риска также есть объяснение.

Готовность: результат воспроизводится вручную, каждый вклад объясним, изменения весов не требуют изменения кода модели.

## 7. Шаг 4 — реализовать денежную оценку без двойного учёта баланса

### Расписание обязательств

1. Для согласованных active/suspended построить платежи в замкнутом интервале `[as_of, as_of + H]`, чтобы платёж ровно в as_of учитывался один раз. Если expiresAt < as_of, сначала пометить противоречие статуса/даты как unknown: не генерировать задним числом сотни пропущенных списаний.
2. Для prolong_wait с `0 <= as_of - expiresAt <= 5 дней` включить текущий неоплаченный платёж ровно один раз. Если срок ещё не наступил или просрочка больше пяти дней — unknown с причиной качества данных. Дальнейшие платежи до восстановления не генерировать в базовом сценарии; это явно указать в описании суммы.
3. Для hour/week добавлять час/неделю; для month/quarter_year/half_year/year — календарные месяцы с правилом последнего дня месяца. Не подменять месяц 30 днями.
4. Для почасовых услуг учесть все платежи в H, а не только ближайший. При большом объёме оптимизировать расчёт, сохраняя результат точной модели.
5. Исключить deleted и blocked. При неизвестных цене/периоде/дате исключить сумму из известного итога и показать количество неоценённых услуг.

### Распределение средств аккаунта

Объединяем обязательства всех услуг клиента и сортируем по времени, затем по ID услуги. Последовательно расходуем общий доступный баланс, сначала основной, затем разрешённые бонусы. Один евро нельзя одновременно зачесть нескольким услугам.

Это сценарий покрытия, а не утверждение, что оплата обязательно произойдёт. В сценарии резервируем средства и для услуги с выключенным автопродлением: возможность ручной оплаты есть, но её неопределённость отражает отдельный признак. Правило показываем в документации.

```text
due_s = сумма платежей услуги в H
unfunded_s = сумма не покрытых балансом частей её платежей
r_s = service_score_s / 100
funding_s = unfunded_s / due_s, если due_s > 0

loss_index_s = due_s × r_s × (0.5 + 0.5 × funding_s)
loss_index_total = сумма loss_index_s по оценённым услугам
```

Коэффициент 0.5 — стартовое сценарное допущение: наличие средств снижает оценку, но не обнуляет риск добровольного непродления. Его также сохраняем в настройках как базовый множитель в диапазоне `[0; 1]`. Финансовый дефицит влияет и на score, и на денежный сценарий; это сознательное усиление, которое необходимо проверить на чувствительность и объяснить жюри.

Название в интерфейсе: **«Сценарная сумма платежей под риском за 7 дней»**. Это эвристическая оценка, не бухгалтерский убыток и не статистическое математическое ожидание. В показатель входят номинальные платежи, в том числе покрываемые бонусами; рядом отдельно показываем основной баланс, бонусы и непокрытые обязательства. Потери денежного потока потребуют отдельной модели.

Пример для одной услуги: к оплате 100 EUR, доступно 20 EUR, дефицит 80 EUR, индекс 70. Сумма под риском = `100 × 0.7 × (0.5 + 0.5 × 0.8) = 63 EUR`. Индекс клиента нельзя умножать на все его услуги: каждая услуга участвует со своим score.

Держим рядом четыре показателя: платежи в H, непокрытые обязательства, сценарную сумму под риском, полноту денежной оценки. Для unknown не подставляем нулевой риск. Если есть неизвестные услуги, итог подписываем как частичный.

Готовность: пример с несколькими услугами использует общий баланс один раз; API, панель и метрики показывают одинаковый итог.

## 8. Шаг 5 — хранение и безопасный пересчёт

Таблицы исходного слоя сохраняют точные поля и ограничения предоставленной схемы. Таблицы приложения: source_snapshots, model_settings_versions, calculation_runs, customer_risks, service_risks, users, sessions. Для истории после запуска — service_status_events.

1. Импорт snapshot проходит проверку до замены данных; замена атомарная.
2. Версия настроек сохраняется транзакционно, с автором и временем изменения.
3. Координатор последовательно обрабатывает версии источника/настроек и периодические события времени.
4. Результат записывается как новый calculation_run и публикуется после завершения целиком. Не смешиваем summary нового расчёта со старой таблицей.
5. При ошибке оставляем предыдущий успешный результат, показываем его время и статус устаревания. После рестарта восстанавливаем опубликованную версию и запускаем пересчёт.
6. PATCH/PUT возвращают 202 с версиями и состоянием задания; SSE сообщает только о завершённой публикации. Для двух конкурентных редакторов используем expected_settings_version и ответ 409 на конфликт.
7. Для первого релиза целевое обновление интерфейса после изменения — до 3 секунд на тестовом наборе. Это цель для измерения, а не заявленная производительность.

Готовность: конкурентные изменения не публикуют устаревший расчёт поверх нового; клиент видит состояние обработки и последнюю успешную версию.

## 10. Шаг 7 — авторизация

1. Создание первого администратора из переменных окружения; нет общего пароля, зашитого в код.
2. Пароли хешируем Argon2id; сессии храним на сервере с ограниченным сроком жизни.
3. Cookie HttpOnly, SameSite; Secure обязателен при HTTPS. Локальный HTTP-режим демонстрации задаём отдельно.
4. Защищаем изменение настроек, snapshot и logout от CSRF; ограничиваем попытки входа.
5. Без входа доступны только форма входа, нужная ей статика и healthcheck без данных. Защита применяется к каждому API, SSE, Swagger и схеме OpenAPI.
6. Prometheus использует отдельный токен только для `/metrics`; он не даёт доступ к данным клиентов. Токен задаётся через окружение и конфигурацию сборщика.
7. Logout отзывает сессию и завершает связанные SSE-соединения. Истечение сессии также прекращает поток.
8. Логи не содержат паролей, токенов, полных snapshots и клиентских email.

Готовность: прямые запросы без входа не обходят защиту панели; сборщик получает метрики без интерактивной сессии.

## 11. Шаг 8 — панель маркетолога

Экраны:

- **Вход:** форма, понятное сообщение об ошибке.
- **Обзор:** количества low/medium/high/unknown, денежные показатели, горизонт, время и полнота расчёта.
- **Рейтинг:** обязательные колонки, сортировки в обе стороны, фильтры, пагинация, переход к клиенту. По умолчанию score по убыванию.
- **Клиент:** услуги, сроки, балансы, включённость бонусов, причины, значения/вклады признаков, расчёт денег, поля с недостаточными данными.
- **Настройки:** веса, пороги, горизонт и сценарный множитель; валидация, состояние сохранения и пересчёта.
- **Данные:** импорт snapshot, отчёт качества и версия; контрольная кнопка импорта доступна только после входа.

Для каждого экрана предусматриваем загрузку, пустые данные, ошибку, unknown и устаревший расчёт. Риск передаём текстом и цветом. Не показываем unknown зелёным и не называем индекс вероятностью.

Готовность: пользователь проходит основной сценарий без обращения к разработчику.

## 12. Шаг 9 — живое обновление

SSE-событие содержит `calculation_version`, `source_version`, `settings_version`, `as_of`; персональные данные в событие не включаем. После события frontend перечитывает таблицу, карточку и summary, сохраняя сортировку, фильтры и страницу.

Настраиваем Nginx без буферизации SSE, heartbeat и повторное подключение. После reconnect сравниваем версию через API, чтобы восстановить пропущенные обновления. При недоступном SSE включаем опрос версии раз в 5 секунд и показываем состояние связи.

Пересчитываем по таймеру даже без новых snapshots: приближение срока оплаты должно менять риск. В демонстрационном фиксированном `as_of` время само не движется; этот режим явно отмечен на панели.

Готовность: две открытые вкладки меняются после одного PATCH/PUT, восстановление связи не требует reload.

Готовность: чистый запуск по README проходит на другом окружении без ручного исправления кода.

## 15. Шаг 12 — проверки, которые подтверждают требования

### Расчёт

- Границы score и уровней, смена весов, отключённый признак, все нулевые веса.
- Unknown при нехватке признаков и частично известном аккаунте.
- Бонусы разрешены/запрещены, withdrawBalance не расходуется, общий баланс не дублируется.
- Каждый paymentTerm, конец месяца, високосный год, UTC и обе границы горизонта.
- Реальный DTO: autoProlong, locked/unlocked, amount 0 и 1000, millisecond UTC, quoted camelCase в PostgreSQL.
- Исходные 6 prolong_wait за пределами пяти дней и 2 просроченных suspended дают предупреждения и unknown; исходник не исправляется.
- Чтение 10/30/100 из JSON, совпадение SQL payload, отсутствие schema_version во входе.
- Реальная миграция/seed на тестовой PostgreSQL; seed повторно отклоняется, PUT snapshot повторно работает.
- Удаление/вставка по FK, сохранность опубликованного расчёта при ошибке замены и корректность identity после явных ID.
- prolong_wait, устаревший snapshot, deleted, blocked, suspended.
- not_performed без истории не интерпретируется как доказанный отказ оплаты.
- Денежный пример 63 EUR, несколько услуг, отсутствие денежных полей и частичный итог.

### API и интеграция

- Все обязательные маршруты и схемы ошибок.
- Четыре обязательные сортировки × два направления, сортировка до пагинации.
- PATCH → сохранение → пересчёт → SSE → согласованные API и метрики.
- PUT корректного snapshot и откат при ошибочном.
- Конкурентные настройки, недопущение публикации старого результата поверх нового.
- Рестарт сохраняет настройки, импорт и доступ; logout отзывает сессию.
- Защита панели, API, SSE, Swagger, схемы и metrics; проверка CSRF.

### Приёмочный сценарий в браузере

Вход → рейтинг → клиент → объяснение score и суммы → изменение веса → обновление в двух вкладках → изменение баланса через snapshot → новый результат → рестарт → настройки сохранились → выход → защищённые данные недоступны.

Готовность: результаты проверок записаны в README/CI; число клиентов и время пересчёта замерены на реальном наборе, а не придуманы.

## 16. Шаг 13 — расширяемость признаков

Каждый признак предоставляет стабильный `code`, название, описание, начальный вес и функцию `calculate(context)`, возвращающую значение или null, причину и недостающие поля. Веса храним по code. Реестр собирает доступные признаки, движок не содержит отдельной ветки для каждого из них.

Добавление признака:

1. Создать модуль в `backend/app/scoring/features/`.
2. Зарегистрировать code и метаданные.
3. Добавить начальное значение к новой версии настроек, сохранив прежние веса.

Готовность: второй разработчик добавляет признак по инструкции, не меняя API-контроллеры и агрегатор.

## 18. Дополнительные возможности после обязательной части

- OIDC с реальным провайдером, входом и корректным logout; простой вход оставляем только при явной настройке.
- График предстоящих непродлений как прогноз; отдельная линия наблюдавшихся переходов в deleted после начала сбора событий.
- Начальные deleted без даты не распределяем по прошлым дням. При snapshot-опросе время обнаружения перехода обозначаем отдельно от фактического времени события.
- Приоритизация по сумме под риском и фильтры для маркетолога.
- После накопления размеченной истории — временное разделение обучения/проверки, оценка качества и калибровка вероятностей. Лишь после этого обсуждаем математическое ожидание потерь.
